# Thapar Talks — Data Flow Diagram (DFD)

## 1. Document purpose

This document gives the complete logical Data Flow Diagram for **Thapar Talks**, a private campus social-networking system for TIET students, student societies, clubs, and event organizers.

It contains:

- DFD notation and drawing rules
- System scope and assumptions
- Context Diagram, also called Level 0 DFD
- Level 1 DFD
- Level 2 DFDs for every major Level 1 process
- External entity, process, data-store, and data-flow dictionaries
- Balancing and completeness checks
- A practical Excalidraw drawing guide
- A short lab explanation and likely viva questions

> **Implementation note:** The current project is a client-side React prototype that uses mock data, React state, and browser local storage. These DFDs describe the intended end-to-end connected system in which the React client communicates with a Node.js/Express API and PostgreSQL. This is a logical DFD, so it shows what data moves and is stored rather than UI components or source-code files.

---

## 2. System overview

Thapar Talks allows verified TIET community members to:

- Sign in with a Thapar email or supported identity provider
- Register and complete a campus profile
- Reset a forgotten password
- View and update profiles
- Follow or unfollow students and campus organizations
- Create, view, edit, archive, restore, and delete posts
- Create, view, edit, delete, and highlight stories
- Create, view, edit, and delete reels
- Browse a personalized feed
- Search students, clubs, and content
- Explore campus content and events
- Like, comment on, save, and share content
- Create direct or group conversations
- Send text and image messages
- Receive and manage notifications
- Configure privacy, theme, and notification preferences
- Report, block, and mute accounts or content
- Log out or delete an account

The first connected implementation is planned as one React frontend, one Node.js/Express API, and one PostgreSQL database. Media files may be kept in media/object storage while their URLs and metadata are stored in the database.

## 3. Standard DFD notation

| DFD element | Meaning | Recommended Excalidraw symbol | Example |
|---|---|---|---|
| External Entity | A person, organization, or external system outside the system boundary | Rectangle | E1 Student / Club User |
| Process | Transforms incoming data into outgoing data | Circle or rounded rectangle | 3.0 Manage Content |
| Data Store | Holds data for later use | Open-ended rectangle or two parallel lines | D3 Content & Media |
| Data Flow | Named data moving between components | Directed arrow | Content submission |

### DFD rules used in this document

1. Every process has at least one input and one output.
2. Every arrow is labelled with the data being transferred.
3. External entities do not communicate directly with data stores.
4. Data stores do not communicate directly with other data stores.
5. Data always passes through a process when it is transformed.
6. Child diagrams preserve, or balance, the external inputs and outputs of their parent process.
7. Process names use verb phrases; data stores and data flows use noun phrases.
8. The DFD does not show buttons, pages, routes, classes, or control timing.

## 4. Scope and assumptions

### Included

- Student and society accounts
- Authentication and onboarding
- Profiles and social graph
- Posts, stories, highlights, reels, and media metadata
- Feed, search, explore, and profile-content retrieval
- Likes, comments, saves, and sharing
- Direct and group messaging
- Notifications
- Privacy, blocking, muting, reporting, moderation, and account deletion

### External services

- **Campus Identity Provider:** verifies supported Google/Thapar identity information.
- **Email Service:** delivers password-recovery messages.
- **Moderator / Administrator:** reviews submitted reports and records moderation decisions.

### Assumptions

- Only approved Thapar identities, normally using an address ending in @thapar.edu, may create student accounts.
- A student society or club account follows the same core profile and content flows, with an authorized operator.
- Authentication secrets are stored securely; plain-text passwords are never stored.
- Media binaries are uploaded to media storage, while content records contain media URLs and metadata.
- A notification may be generated by a follow, publication, interaction, message, mention, report outcome, or account event.
- Search and feed results respect privacy, block, mute, deletion, and archive status.
- Archived content remains available only to its owner until restored or deleted.
- Stories may expire from normal viewing while highlighted stories remain available.
- Shares primarily return a shareable content link; no third-party social platform is required inside the system boundary.

## Level 0 flow explanation

1. A student or club user supplies account details, content, queries, interactions, messages, settings changes, or reports.
2. Thapar Talks validates and processes the request.
3. The system may request identity verification from the Campus Identity Provider.
4. The system may ask the Email Service to deliver a password-reset message.
5. Submitted reports are made available to a moderator, whose decision is returned to the system.
6. The user receives results such as a session, feed, profile, content, messages, notifications, or operation confirmation.

## 6.4 End-to-end Level 1 narrative

1. The user first enters through **1.0 Authenticate & Manage Accounts**. Account and session information is read from or written to D1 and D2.
2. After authentication, the user can maintain a profile and follow relationships through **2.0 Manage Profiles & Social Graph**.
3. The user publishes and manages posts, stories, and reels through **3.0 Manage Content**, which stores content and media metadata in D3.
4. **4.0 Generate Feed & Discovery** combines profiles, visible content, follow relationships, engagement signals, and safety filters to produce the home feed, search results, Explore, Reels, and profile grids.
5. Likes, comments, saves, and shares pass through **5.0 Manage Engagement** and are stored in D5.
6. Direct and group chat operations pass through **6.0 Manage Messaging** and are stored in D6.
7. Events from social, content, engagement, messaging, and safety processes enter **7.0 Manage Notifications**, which stores and returns user notifications.
8. Privacy preferences, blocks, mutes, reports, moderation decisions, and account deletion pass through **8.0 Manage Settings, Safety & Moderation**.

# 19. Two-minute lab explanation

“Our project is Thapar Talks, a private campus social platform for TIET students and organizations. In the Context Diagram, the complete application is represented as Process 0.0. Its main external entity is the Student or Club User. The platform also communicates with a Campus Identity Provider for verification, an Email Service for password recovery, and a Moderator for report decisions.

In Level 1, the system is decomposed into eight processes: account authentication, profiles and social relationships, content management, feed and discovery, engagement, messaging, notifications, and settings or safety. The system uses eight logical stores for accounts, sessions, content, social relationships, engagement, messages, notifications, and safety preferences.

For example, when a user creates a post, the content first enters Process 3.0. The author and submission are validated, media is stored, and the post record is saved in D3. Process 4.0 later reads that content, the user’s follow graph from D4, engagement signals from D5, and safety filters from D8 to create the feed. If another user likes or comments on the post, Process 5.0 stores the interaction in D5 and sends an event to Process 7.0, which creates a notification in D7 for the post owner.

The current React prototype performs these operations with mock data and local browser state. The DFD represents the intended connected version using the planned Express API and PostgreSQL database.”

# 20. Likely viva questions

### Why is the database not shown in the Context Diagram?

The Context Diagram treats the entire application as one process and shows only its communication with external entities. Internal data stores appear from Level 1 onward.

### Why is the Campus Identity Provider an external entity?

It is outside the Thapar Talks system boundary and only returns an identity-verification result.

### Why are React components, API routes, and PostgreSQL tables not shown?

A logical DFD describes data movement and transformation, not program structure or physical implementation.

### What is DFD balancing?

The external inputs and outputs of a parent process must remain represented when that process is decomposed into a lower-level diagram.

### What is the difference between D3 and D5?

D3 stores the actual post, story, or reel and its media metadata. D5 stores user activity associated with that content, such as likes, comments, saves, and shares.

### How is a personalized feed generated?

Process 4.0 combines visible content from D3, following relationships from D4, engagement signals from D5, and privacy or block filters from D8, then ranks and paginates the result.

### How does a like create a notification?

Process 5.0 validates and stores the like in D5, then sends a like event to Process 7.0. Process 7.0 checks the recipient’s preference, builds the notification, and stores it in D7.

### Where are passwords stored?

The logical account store contains only a secure credential reference or password hash. Plain-text passwords must never be stored.

### How are archived posts different from deleted posts?

Archived posts remain in D3 with restricted owner-only visibility and may be restored. Deleted posts are soft-deleted or removed according to the retention policy and do not appear in normal retrieval.

### Why does account deletion touch several stores?

An account owns sessions, content, relationships, engagement, and conversation memberships. Process 8.7 must revoke access and consistently delete, deactivate, or anonymize dependent records.
